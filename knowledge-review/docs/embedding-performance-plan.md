# Embedding 耗时拆解与复用评审方案

日期：2026-10-24。状态：**待用户评审，尚未添加计时、运行本方案或实现模型池**。第一步只测量现状，第二步根据结果单独决定。最终回答质量评测不在本方案内。

## 1. 要回答的问题

1. 跨问答反复创建模型、计算指纹，占一次实际搜索多少时间？
2. 向量全部命中磁盘缓存后，仍有哪些初始化、读取、解析和排名成本？
3. 同一工具实例里的暖查询，和当前网页每轮新建工具的耗时相差多少？
4. 如果考虑模型复用，收益能否抵消内存常驻、同步锁及配置管理的成本？

当前调用入口是 `web_app.generate_answer → KnowledgeTools → LocalEmbedder`。每轮工具实例独立；`LocalEmbedder` 首次搜索才加载。`cache_profile()` 每个模型实例首次计算加载权重与 tokenizer 指纹，`get_document_vectors()` 内部调用它。

已有 `KnowledgeTools.retrieval_trace` 可以复用，但 `query_embedding_ms` 当前从访问 `self.embedder` 前开始，因此首次调用包含模型初始化，不能直接解释成纯查询编码时间。向量缓存总耗时中也混有指纹计算和缓存缺失时的正文编码。

源码入口：[web_app.py](../web_app.py)、[knowledge_tools.py](../knowledge_tools.py)、[embeddings.py](../embeddings.py)、[vector_index.py](../vector_index.py)。

## 2. 第一阶段：最小计时改动

使用 `perf_counter_ns()` 记录墙钟时间，保持原调用顺序与懒加载。不为计时额外调用编码、指纹或搜索，不强制刷新缓存。计时默认关闭，由独立测量入口显式启用；API 正常响应与引用范围保持现有契约。

| 阶段 | 计时边界 | 需要附带的计数/状态 |
| --- | --- | --- |
| 依赖导入 | 首次导入 sentence-transformers 等本地库 | 当前进程是否首次 |
| 模型加载 | `SentenceTransformer(...)` 构造及必要配置 | 模型配置、设备、有效输入上限、成功/异常类型 |
| 查询编码 | 模型已获得后，仅 `embed_query()` | 查询 ID、编码窗口数；不存问题正文 |
| 片段准备 | `prepare_chunks()` | 原始/预处理片段数量 |
| 指纹计算 | `cache_profile()` 内首次计算分支 | 新算/实例缓存命中、耗时；包括权重哈希和 tokenizer/runtime 信息 |
| 向量读取 | 打开/初始化 SQLite、SELECT、JSON 解析、校验 | 内存命中、磁盘复用数、缺失数；与指纹阶段分开 |
| 正文编码 | 缓存缺失时的 `embed_chunks()` | 编码片段/窗口数；全命中时明确为零 |
| 缓存写入 | 编码完成后的序列化和事务提交 | 写入数、成功/异常类型 |
| 排名 | 沿用并核对 dense/BM25 建立/BM25 搜索/RRF 分段 | 许可片段数、各路候选数 |
| 整次搜索 | `search_notes()` 外层 | 总时间、状态、未归属时间 |

父子阶段不直接相加。例如向量缓存总时间包含内部指纹/正文编码，只在报告里展示其独占时间或标明嵌套。未归属时间保留，避免强行拼成一个看似精确的总和。失败记录已完成阶段和失败点，不把失败当零耗时。

建议输出 `.data/evaluations/embedding-timing-<时间>/samples.jsonl`、`summary.json`、`report.md`。只保存公开样例 ID、配置/源码版本、数量、时间和异常类型，不输出私人原文、密钥、请求头或服务地址凭据。

## 3. 可重复的测量矩阵

固定当前公开 `evals/retrieval/expanded-v1/corpus/`、许可范围、模型、CPU 线程数、查询顺序和检索模式。只用本地已准备的模型，不请求云端生成，不下载新模型，不改历史评测数据库。

| 场景 | 实际执行方式 | 主要目的 |
| --- | --- | --- |
| A：进程首次使用、空向量缓存 | 3 个新子进程，每个独立空索引；首次搜索单列 | 测依赖导入、模型初始化和正文编码 |
| B：进程首次使用、已有向量缓存 | 5 个新子进程，复用本方案专用的预建索引 | 区分模型加载/指纹与向量重建 |
| C：当前网页的实例生命周期 | 同一进程，每次新建 KnowledgeTools，20 条公开查询各重复 3 次 | 测跨请求重复成本；各实例第一搜均计入 |
| D：同一工具实例连续搜索 | 同样 20 条查询各 3 次；首次搜索另外报告 | 测暖编码和排名下限，不能称生产跨请求性能 |

“进程首次使用”不保证磁盘/操作系统缓存为空；不清理操作系统缓存，也不把它称为物理冷盘。A/B 的首次值用逐次原值及中位数描述，3/5 个样本不包装成稳定 P95。C/D 报 P50/P95、样本数和范围，60 次记录也不是 60 个独立质量案例。测量顺序与其他 CPU 工作隔离，保留所有样本。

附版本、设备、线程数、模型配置/指纹、片段数、缓存命中数、总耗时。内存如有可靠进程 RSS 工具则记录峰值/稳定值，否则明确缺失；`tracemalloc` 无法完整代表 PyTorch 原生内存。

## 4. 测量后怎样决定

- 初始化和指纹若在“新工具＋磁盘全命中”场景中反复占据显著时间，优先评审模型实例复用。
- 正文编码占主导，先检查是否存在合理的新资料/输入变化或异常缓存失效；模型池不能消除真正需要的正文编码。
- 向量读取或排名占主导，模型池未必是首选；按实际片段规模定位 SQLite 读取/反序列化或精确排名成本。
- 短资料可能无需 `search_notes`；本方案的纯搜索结论不能直接换成整个 Agent 或聊天首段正文的收益。

建议的评审触发条件是重复成本在多次观测中达到数百毫秒、或占搜索总耗时的明显比例；这是项目判断依据，未预先承诺节省数值。由阶段占比和实际使用频率决定，不为使用模型池而增加结构。

## 5. 若确认有收益，第二阶段的最小复用设计

优先在每个 FastAPI 应用实例的 lifespan/state 内保留一个当前配置的 `LocalEmbedder` 提供器，通过 `KnowledgeTools` 已有 `embedder` 注入点使用。当前是单模型配置，暂不设计通用 LRU 多模型池。

1. 初始化使用锁，仅第一次实际需要时创建；初始化失败释放锁并允许后续请求重新尝试，不缓存半初始化对象。
2. 一个实例对应固定模型制品版本、EmbeddingConfig、设备/dtype、有效 token 上限与 tokenizer。模型缓存按只读制品使用，模型/配置更新通过重建实例或重启生效，不在活跃请求中修改模型。
3. 权重指纹在该实例首次需要时计算一次；持久向量缓存原有来源/输入/参数失效规则全部保留，不能只用模型名字作为缓存身份。
4. 初版用推理锁保护模型/tokenizer 的相关访问，先保证安全；分别测并发 1/2/4 的吞吐、P95 和内存。串行推理锁可能改善内存却降低吞吐，要据此决定是否继续复用或采用有限实例数。
5. 每个请求继续独立构造 KnowledgeTools、许可 sources、prepared chunks、`_vectors`、BM25 和可见证据。复用模型不授予跨请求资料权限。
6. CLI、独立评测与会话记忆不自动切换生命周期。多进程部署各进程仍有自己的模型副本，不能宣称跨进程共享。

第二阶段验收应同时检查排名/分数不变、权限范围不扩大、并发初始化只发生一次、失败可重试、懒加载有效，以及上述四种场景的实测变化。无需为此修改既有检索标签或增加云端答案评测。
