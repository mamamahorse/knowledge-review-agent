## 2026-10-08：质量评测与核心代码梳理

### 1. 接口测试通过，仍不能说明知识整理质量

- **问题**：当前最近记录为 184 项 unittest 通过；多数测试使用受控模型结果，真实样例分散在忽略目录中，没有统一的参考标注和评测入口。原文分析完毕也不能说明所有概念都已提取。
- **方法**：新增版本化合成资料与参考标注，复用真实提取、归组和评分服务，在独立数据库运行；将程序规则、参考标注一致性和人工语义复核分别报告。
- **为什么**：单元测试适合验证事务、预算和身份；语义质量需要固定资料与可核对的预期。用同一个模型给自己的结果打分，容易掩盖相同盲点，因此第一版保留人工匹配和审核入口。
- **限制**：本次参考标注由开发时编写，尚待用户人工确认；报告必须标为草案参考，不能称为已完成专家标注或全库质量校准。

### 2. 评测不能污染正式数据或自动触发模型调用

- **问题**：网页模块在导入时创建默认应用，会连接正式数据库；直接复用网页初始化来评测可能产生不必要的正式库访问。
- **方法**：评测直接调用业务服务，不导入 `web_app`，每次运行在 `.data/evaluations/` 的新目录创建专用数据库。默认仅校验资料；真实模型模式必须显式选择，受控模式用于验证评测器本身。
- **为什么**：业务服务已经包含预算、证据和状态边界，复用它们能测到实际行为；隔离存储使重复运行可比较，也避免把测试目标写进学习计划。
- **验证**：全套受控运行完成六组资料与四组评分，59 次逻辑任务请求；每组专用库的 ReviewItem/ReviewEvent 均为零。默认离线入口用受控测试确认没有调用模型或初始化业务数据库。正式库数量比较见本节末验证记录。

### 3. 用户需要从业务链路理解核心代码

- **问题**：项目已有模块职责表，但单纯按文件逐个阅读不容易看出请求、模型结果和数据库记录怎样衔接。
- **方法**：按持续问答、清单提取、归组加入、作答评分、评分修订五条链路建立阅读路线，定位入口函数、关键数据对象、写入边界和现有测试。
- **为什么**：从一条真实业务路径追踪数据，比先读全部模块更容易理解每个设计选择；尤其能解释资料权限、模型与程序职责、幂等和 FSRS 重放。
- **验证**：`docs/core-code-walkthrough.md` 已按实际入口、服务、存储函数及现有测试名称建立五条路线。重点解释共同 ContextBundle、原文可见范围、候选/归组 revision、加入事务和原时间/参数回放。

### 4. 新评测器的接口接入与 Windows 文件占用

- **问题**：首次受控运行把引用对象直接传给需要 source_id/start/end 的函数，又给只接受关键字语言参数的评分服务传了位置参数，出现 TypeError。测试还误以为 `with sqlite3.connect(...)` 会关闭连接，Windows 清理测试目录时提示文件占用。
- **方法**：核对真实函数签名，展开引用字段，用 `response_language=...` 传参；测试连接使用 `contextlib.closing()` 显式关闭，再清理本次拥有的目录。
- **为什么**：评测必须复用现有业务契约，不能为接线方便改动稳定的生产接口；SQLite 上下文管理控制事务而不关闭连接，不能依赖垃圾回收释放文件。增加完整服务接线测试，防止只测试报告格式而漏掉真实调用错误。
- **验证**：专项受控测试通过。修改仅在新增评测器及其测试，未重写现有服务。

### 5. 部分运行与覆盖行数容易被当成质量分数

- **问题**：真实分层样例在 4 次任务上限后仅保留概述，尚未生成候选；测试最初断言“没有提取就应为 0 已处理行”，但一个仅标题范围已由程序处理，因此为 1/66。smoke 若填完整审核，也不应得到模型语义质量比率。
- **方法**：报告分别记录原文处理进度、阶段状态、草案一致性与人工语义匹配；完整真实提取及对应审核全部完成后才计算比率。调用上限明确标部分运行，保留数据库和报告；smoke 永不输出语义比率。
- **为什么**：将不完整结果除以全部参考点会混合预算策略和语义遗漏，将程序空白处理视作知识理解同样误导。留存失败比自动重跑直到成功更能暴露稳定性问题。
- **验证**：新增分层调用上限测试确认已完成概述保留、后续未完成、原文进度小于总数；不完整审核、旧结果指纹、未知身份和 smoke 比率测试通过。

### 6. 参考标注自身存在解释空间

- **问题**：题设已经写明纯数据/顺序条件；学生答案正确给出 ACK=130 和下一个期望字节，但没有重复条件，整体是否达到标准存在不同理解。不能把开发时的一个判断当成专家唯一答案。
- **方法**：保留逐标准的草案分类，整体判断允许 developing/meets_standard，写明理由；所有标注标为待人工确认。真实提取使用人工候选映射和条件/语义证据审核，不使用标题关键词匹配或同一个模型自评分。
- **为什么**：题目歧义是评测需要发现的问题；把模糊参考强制成唯一标签会把合理模型判断误判为错误。精确身份可用于固定候选关系比较，开放式知识提取则需要语义复核。
- **验证**：真实四种固定答案的整体判断、范围及逐标准分类均与当前草案一致；这只能说明这四个样例，不说明全局评分校准。

### 7. 首批真实模型结果与限制

- **运行方法**：显式 live，沿用当前配置，使用合成资料专用库；没有调整模型、提示词或输出预留来追求成功。
- **实际结果**：第一份 8 次任务运行中，小型 TCP 全文提取失败且未发布候选；重复目标资料提取完成、固定 ACK 解释/应用及 RESET 重复关系符合草案；四个固定作答评分完成且与草案一致。另一次 2 次归组运行没有合并不同含义的窗口，并将 TTL 数值冲突标为待核对。

- **保留**：报告路径在评测说明的验证记录列出。所有失败尝试独立保存，不用后一次成功覆盖首轮失败。

## 2026-10-09：大候选集自动分层整合

### 1. 输入能容纳，不代表输出可以表达完整工作

- **问题**：旧归组只比较一次，最多 4 个建议/每组 8 个成员；超预算需用户手动缩小范围，没有剩余工作回执。
- **方法**：新增完整 Schema 请求预算及明确标注的输出估计，选择直接或按章节/预算分层。模型必须对程序给定的比较身份返回已处理/待处理回执；回执缺失、重复、未知拒绝。建议槽位已满时，未报告关系的比较继续处理。
- **为什么**：不能把模型没返回的关系自动当成不存在，也不能通过候选数量的任意阈值猜测服务容量。输出估计是启发式，回执和续处理兜底，不宣称语义完备。
- **实际接入问题**：旧受控归组测试仍返回没有回执的 GroupDraft，新协议正确拒绝，因此多项测试失败。补上受控比较回执，保留原有审核/事务断言；旧数据库任务仍保留旧执行分支。

### 2. 卡片压缩与跨批遗漏

- **问题**：再让模型压缩条件可能损失细节；只比较相邻批次或只让已归组内容向上参与，会漏掉远处章节和独立候选。
- **方法**：导航卡片保留完整候选知识、范围、标准、能力和证据指针，仅移除原文正文。稳定章节叶节点和二叉上层节点分配全部候选对；上层筛选的关联补回固定原文核验。
- **为什么**：卡片不新增知识，也不扩大引用权限；程序可以解释每对候选在哪个节点处理。第一版不引入字面/向量筛选排除关系。
- **代价**：最坏候选对工作量为平方级，不能承诺海量资料固定调用数。每次明确模型请求额度，达到后暂停；用户继续才增加额度，完成步骤复用。

### 3. 关系链不能证明大组可合并

- **问题**：A 与 B、B 与 C 有关系，不自动证明 A 与 C 条件一致；直接连通分量合并可能抹去条件差异。
- **方法**：只从实际原文核验的关系组成组，扩入成员时要求与每个已有成员有同类型支持；待核对关系阻止确定合并。超过旧 8 人限制的大组由多步证据支持，保留步骤来源和原模型结果。
- **为什么**：避免把传递关系当作模型已经检查过的结论；仍是用户可拒绝的建议，不改变已有目标或 FSRS。可能形成重叠备选组，沿用审核冲突保护。

### 4. 续跑必须保留发布边界

- **方法**：在原业务库增加步骤及运行计划/额度字段，旧记录默认 plan=NULL；网络不占写事务。每次请求先记录 attempt 和额度，返回后复核资料、候选版本及运行 attempt。暂停、中断或版本变化不发布迟到结果；全部计划内比较/必要核验完成后才原子发布审核建议。
- **为什么**：部分模型结果可以保留查看，但不应在尚未完成整合时被误认为最终审核结果；旧任务不被新协议强制重新解释。
- **验证**：见下方本步收尾记录；不把受控接口结果当成真实语义效果。

### 5. 进度刷新不应覆盖正在编辑的额度

- **问题**：检查前端时发现归组区每次重绘将额度重新设为 24；后台轮询或审核后的刷新会覆盖用户输入。未准备好计划时也曾直接显示“分层比较”。
- **方法**：按清单 ID 保存本页额度草稿，重绘复用；无路由时显示正在准备。组装大组时按稳定成员对顺序选展示依据，完整原始回执仍保存在步骤中。
- **为什么**：额度是用户明确控制请求次数的输入，不能在提交前被后台刷新改变；稳定展示方便解释恢复后的结果。
- **验证**：受控页面填写 5，保存另一个建议导致重绘后仍为 5；刷新/重启恢复原比较与审核代表，页面无脚本错误。额度草稿只在当前页面保留，整页刷新仍默认 24，运行已授权额度在 SQLite 持久保存。

## 2026-10-23：网页连接失败缓存、重复登录与取消后的弹窗循环

**现象与复现：** gateway.js首次探测使用固定ready Promise，网络失败或503后后续业务始终复用同一失败；并发请求迟到的401可在登录完成后再次弹窗；等待login Promise的请求收到AbortSignal仍不退出。旧版9项隔离Edge场景4通过、5失败。限流/繁忙JSON使用error.code，但原页面只识别detail，因此用户只看到笼统失败。

**定位与修复：** ensureReady仅在失败时清除当前初始化Promise，让后续操作重探；authVersion标记成功登录代次，只有属于当前旧代次的401才打开/等待登录。waitFor为单个调用注册并清理abort监听，不取消共享登录。错误映射只处理已知Gateway错误，保留原Python响应；Retry-After只展示有效整数，不调度自动重试。只有明确在转发前拒绝的401最多重发一次。

**完整页面又发现的根因：** 增加取消登录按钮后，sendChatSubmission的finally仍无条件loadChat，新的鉴权请求立即再次弹窗。区分本请求controller主动停止与登录取消；后者恢复发送按钮并保留输入，不发起自动历史请求。真正生成取消的历史确认仍保留。完整UI检查先失败、修复后通过。

**测试工具问题：** 部署前覆盖app.js的匹配最初遗漏?v=...，实际仍加载旧脚本，导致修复后表象不变。记录请求和页面状态后定位，匹配查询参数并断言实际覆盖一次；最终使用没有任何源文件覆盖的镜像再次通过。临时请求/页面日志不含Key或私人资料。

**结果与边界：** 新增登录取消场景后10项浏览器检查、原SSE解码5项、最终镜像页面的限流/过载/输入与request_id保留/取消与重连全部通过；三服务healthy、89份运行文件与当前源码匹配。本轮不增加模型调用、容量实验或全量回归，也不自动提交/推送。步骤和命令见Gateway的docs/development/2026-10-23-web-recovery.md。
