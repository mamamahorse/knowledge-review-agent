# Knowledge Review：清单直接提取 V2 与长资料整理方案

日期：2026-10-26。状态：设计建议，尚未实现或进行 V1/V2 模型实验。

本文根据当前源码评审用户提出的 V2。代码事实、工程判断、待实验验证分别注明；不推断最初开发者的个人动机。

2026-10-26 补充：任务识别、完整功能目录及 `ask_question` 持久澄清设计见 [任务识别与交互方案](task-routing-and-clarification-proposal.md)。这使聊天路由成为显式设计范围；先固定能力与等待契约，再接入实际可执行的清单/总结任务。

## 1. 结论与当前实现核对

建议采用：**复用文档结构，按完整请求预算打包原文，以主要提取范围为单位直接生成候选；只在明确需要综合报告时增加汇总。**

这项建议有两个独立交付范围：A 是清单提取算法 V2；B 是让“整理/总结整份资料”有明确的产品入口和执行流程。只完成 A，普通聊天仍不会自动获得全资料分析能力。

| 当前代码事实 | 位置与说明 |
| --- | --- |
| 候选归组的分层比较 | `outline_group_plan.py:48 make_plan`、`:85 work_scopes`；处理已经提取出的学习候选。叶节点进行原文比较，跨节点卡片生成关系假设，再由整合流程核验。这不是原文摘要树。 |
| 原文的全文/分层提取 | `outline_context.py:81 plan_outline`、`:227 run_adaptive`。长文先做窗口概述、章节概述、文档概述，再结合原文提取学习候选。 |
| 规划器本身不调用模型 | `plan_outline` 只规划；概述 API 调用实际发生在 `execute_step` 和 `reduce_steps`。 |
| 全文路由使用启发式 | `max(正文块数, ceil(UTF-8 字节数 / 500), 1)` 估计目标数；还检查不超过 6 个、估计输出和完整输入预算。该公式不是知识点密度测量。 |
| 分层初始窗口上限为 80 行 | 先二分检查容量，再尽量退回 Markdown 块边界。它已经考虑结构，但不是直接使用统一 ContentBlock 打包。 |
| 仍然读取原文提取 | `run_adaptive` 最终提取请求包含原文，概述只是背景；不能将现状描述成“仅从摘要提取”。 |
| 清单有特殊入口 | `web_app.py:540` 附近的集合清单接口调用 `plan_outline`；普通 `run_agent` 没有自动调度这套工作流。 |
| 现有测试证明执行机制 | `test_outline_context.py` 检查概述复用、原文补回、预算缩批、暂停及版本拒绝；受控模型响应不能证明真实语义收益。 |

因此，用户关于“特殊逻辑局限于清单工作流”的判断成立。原文概述树的额外调用是确定存在的，但其净成本、召回收益和失真程度需要实测，不能直接宣称当前质量差。

## 2. 先区分任务，再区分处理规模

建议产品层明确三种任务：

| 任务 | 资料访问策略 | 结果 |
| --- | --- | --- |
| 局部问答 | 现有 Agent 按需搜索/读取 | 针对问题的回答及引用 |
| 提取学习清单 | 遍历选定资料的可处理结构块 | 知识点、可考察目标、标准及原文依据 |
| 整理/总结资料 | 遍历资料，按章节收集要点和条件，再组织报告 | 章节摘要、关键概念、跨章节关系、未覆盖项 |

**为什么不只按“大文件”路由：** 同一本书的单点问题可以检索，短而密集的规范全文提取也可能需要多个输出窗口。路由应由任务意图、范围、输入容量和输出压力共同决定，文件大小仅作诊断。

第一版建议使用显式“问答 / 整理资料 / 提取清单”入口。聊天自然语言自动触发可作为随后一层适配：模型提出有限枚举的任务类型，程序验证资料范围并调用同一后台作业接口；模糊请求保留范围确认，不能仅凭“总结”关键词触发整库处理。后台结果以任务 ID 和进度卡展示，避免把长作业绑定在一次聊天 HTTP 等待中。

小资料可由同一规划器产生一个窗口，大资料产生多个窗口及持久进度；不必复制两套业务代码，也不能继续以少量 Top-K 命中冒充全文处理。

## 3. 推荐的清单 V2 流程

`资料快照 → ContentBlock → 结构拆分 → 完整请求预算打包 → 原文直接提取 → 范围/证据校验 → 输出压力检查 → 批次提交 → 可选归组与用户审核`

### 3.1 复用结构，独立规划提取窗口

直接复用 `Source.document`、`Document.blocks`、`heading_path`、原文行号、表头及 `context_ranges`。`sources.py:18` 会为 Markdown 构造结构，PDF 从持久快照恢复。

复用 `chunking.block_chunk`、`with_table_context`、`table_reading.table_rows` 等位置和依赖处理能力；不要把 `chunk_source(max_chars=1200)` 或 E5 的编码窗口直接当成生成窗口。它们服务检索，预算和输出目标与清单提取不同。

在提取层建立结构块序列；跳过纯导航占位，保留其未解析记录。标题提供章节路径，正文构成主要提取单元。发现块重叠、缺口或范围越界时显式报告，而不是假定解析结构永远完整。

选择结构块的原因：确定性、成本低、保留原文位置，容易测试。Embedding 语义切分和额外 LLM 切分暂不作为默认：增加依赖、延迟和不确定性，当前没有质量证据证明需要它们。若结构质量很差，应单独评测补充分块策略。

### 3.2 原文窗口分成主要范围和辅助范围

建议提取窗口保存如下概念字段，名称可在实施时沿用仓库风格：

- `primary_ranges`：本批负责提取的原文范围；基础规划时各批互斥。
- `support_ranges`：真实表头、单位/脚注、邻近原文和定向补读的定义，可以在多批重复出现。
- `heading_paths`：导航信息；标题路径本身不授予未发送正文的引用权。
- `source_id`、`block_ids`、`planner_version`：来源及算法身份。
- 输入估计、输出预留、拆分父项、未解析项：用于诊断与恢复。

校验规则：所有引用必须落在真实发送的主范围或辅助范围；每个学习候选至少有一个主范围证据锚点。辅助材料可以支撑定义或条件，但不能独自生成本批的新目标。单靠“至少一个锚点”仍无法证明目标语义属于本批，语义越界需要抽样审核。

为什么不用无差别 overlap：它会增加重复目标和覆盖统计混乱。主辅分离既能补上下文，又能明确本批的工作归属。

### 3.3 按完整请求预算贪心打包，但不追求把窗口塞满

按原文顺序尝试加入相邻块，原则上不跨不相关章节；将标题路径、原文、必需表头/脚注、任务说明和真实 Schema 全部装成待发请求，再调用 `fits_request`。若加入失败，提交当前窗口；单块仍失败则进入结构拆分。

容量约束：

`完整请求输入估计 + 输出预留 + 安全余量 ≤ 已配置上下文容量`

还要满足单独的最大输入/输出限制（若服务提供）、章节边界和提取窗口软上限。输入容量是硬上限；适宜提取窗口是需要评测的较小目标，不应因为模型支持长上下文就一律塞满。

在同一预算下，小资料自然合为一个窗口。规划阶段可缓存不可变块的计数、按块边界查找可装入前缀，最终仍对真实拼装请求检查；不能把分块 token 数简单相加视为协议的精确值。

当前 `GenerationBudget.estimate` 是 UTF-8 字节估算，不是模型 tokenizer。V2 初期可以沿用这个有标签的保守接口，用于控制改动范围；接入匹配实际服务模型的计数适配应作为独立改动。不能使用 E5 tokenizer 计算生成模型上下文，也不能同时改变计数器后把全部收益归因于分块算法。

**待实验：** 选择不同的窗口软上限、邻近上下文额度，比较遗漏、重复和延迟。当前没有依据给出通用最佳 token 数。

### 3.4 超大块的拆分规则与真实限制

| 内容 | 建议策略 | 必须保留的边界 |
| --- | --- | --- |
| 段落 | 先段落边界，仍过大时优先合理的句末/换行边界 | 不改写源文本；单行切句见下文 |
| 列表 | 按列表项，必要时拆子项 | 带上限定范围的父项原文；列表层级只是导航时不能变成证据 |
| 表格 | 按可验证的行组分批 | 每批附真实表头、单位、必要脚注，分别记录原文位置；不得把表头和远处行伪装成连续区间 |
| 代码 | 优先现有结构和空行等逻辑边界，其次完整原文行 | 标记片段不完整，保留必要签名/上下文；首版不新增跨语言 AST 框架 |
| 图片/公式 | 可可靠读取的文本参与处理，未知占位记录 unresolved | 纯图片标签不能当图中事实；视觉处理为显式受预算约束的路径 |

现有表格工具主要依据可解析的 Markdown 表行。超宽单行、合并单元格或不可可靠分页的提取结果，应标记待处理；“行组处理”不能宣传为解决所有复杂 PDF 表格。

**特别注意超长单行：** `context.validate_chunks` 要求 Chunk 文本等于完整原文行；`Citation` 目前按行授予权限。把一行切成两个句段，然后给每段完整行号，会错误扩大模型可引用内容。

最小可交付 V2-A：保留现有行级契约，处理可按完整行拆分的块；单行仍超预算则持久化为未处理原因，继续其他可处理批次。不能称其已经支持任意超长段落。

如真实资料确实存在较多超长单行，V2-B 再增加派生的精确片段表示：来源版本、原始行定位、明确的字符偏移/精确原文范围、实际送达文本。偏移单位及换行处理必须固定；校验按范围而不是整行权限进行。无需重写解析器，但必须贯通格式化、候选编辑、归组、加入计划和引用展示；旧消费者不能忽略偏移后放大权限。这是有实际接口成本的扩展，不应藏进“一句按句子拆分”。

### 3.5 原文直接提取与输出压力控制

每批直接生成现有 `LearningProposal`。取消 V2 提取前的窗口/章节/文档概述树；保留章节路径和原文支持材料。现有 `OutlineDraft` 每批最多 4 个目标、`FullOutlineDraft` 最多 6 个；单纯扩大输入窗口而保留这组固定上限，会增加遗漏风险。

建议提供 V2 专用结果封装，候选本体仍复用 LearningProposal；增加待核查/疑似未覆盖的原文范围、有限未解决项和覆盖风险。输出仍设上限，防止无限长 JSON；提示中的提取粒度由任务配置清楚表达，不能一边要求全面提取一边只要求“小而有用的一组”。

以下信号触发风险处理：服务输出截断、候选数达到上限、模型报告剩余范围、输出预算逼近上限（若有 usage）。这些是风险信号，不是遗漏的证明；模型声称完成也不是完整覆盖的证明。

对可拆分窗口，在完整结构边界缩小主范围再提取；达到最小可拆单元、拆分深度或作业调用/费用额度上限时保留“覆盖待核查”，而非无限重试。网络失败沿用有限重试，不一律靠拆块解决。

父批的饱和结果保留为诊断，尚不发布为正式候选；缩批时事务性建立完整子批并将父批标记为被替代。只有有效叶批生成正式候选，避免父批与子批重复入库。已完成并被用户编辑/采用的候选不因后续策略改变而悄悄重写。

上限触发可能对“刚好等于上限且已完整”的结果产生额外调用，这是保守覆盖策略的成本，应在实验中报告误触发及增加的调用数。对低于上限仍遗漏的情况，必须用参考标注检验。

### 3.6 跨章节依赖：只在确有缺口时补原文

先用章节路径、真实表头和少量邻近原文。若当前块明确引用其他章节或缺少必要定义，允许有界补读：由模型提出原文定位/检索请求，程序检查资料范围、预算和实际返回片段，将其作为 support。

不预先为所有窗口生成全局摘要，也不默认给所有窗口塞一份全局术语表。这样减少固定前置成本，但可能损失隐含的远距离依赖。补读的必要性、额度及质量收益需要跨章节资料实验，首版可以先记录 unresolved 后手动复查，再决定是否加入自动补读。

## 4. “整理/总结资料”需要独立的结果流程

清单输出的可考察目标与自然语言报告不同，不应将 LearningProposal 生硬转换成所有总结任务。

建议共享结构窗口规划和证据边界，使用单独的报告结果类型：每个窗口直接提取有依据的概念、结论、条件、例子、未解决项；按原章节顺序组织，结果可展开并回到原文。小资料可以一次直接生成所需报告。

对于大资料：

1. 章节式整理允许保留多节结果，不强制把整份书压成一个短回答；先确保处理范围和缺口可见。
2. 用户需要“全书总览/章节关系”时，再从这些结构化要点进行有界综合；必要时按章节或主题分组，保留详细结果，不无限把全文反复压成固定六点。
3. 综合请求只有要点和证据指针时，将输出标为派生综合；程序可追溯引用血缘，但不能宣称综合模型已经读取所有原文。涉及新关系或争议结论时补读原文，再允许形成新的有依据结论。

最终概括本身就是有损选择。不能承诺“完全不压缩还输出短篇全书总结”；应明确用户要的是快速概览、逐章整理还是尽量完整的清单。

该流程为新增能力，需要独立结果存储/API 和界面。复用已有快照、执行准入、取消、持久步骤模式，不把摘要假装成 outline_candidates，也不趁此重写一个通用工作流平台。

## 5. 归组保留独立，注意总成本转移

`outline_group_plan` 的分层关系比较解决候选重复、范围及先后关系问题，不能随删除概述树一起删除。

V2 先允许用户查看原始候选，归组作为独立操作。只对确定的相同身份/完全重复提交做确定性去重；相似标题不等于相同目标。语义合并仍应保留原文条件与审核。

当前 `comparisons` 显式生成全部候选对，最坏比较规模为 n(n−1)/2。分层划分不等于消除了二次复杂度。若 V2 提高召回并产生更多候选，归组成本可能上升，不能只测提取阶段就宣布端到端节省。

以后若需要改为候选检索后局部比较，必须单独验证跨章节重复/冲突的召回；本轮不把该算法改动并入提取 V2。

## 6. 持久化、恢复和旧任务兼容

建议清单计划增加独立的 `plan.version=2` 与策略身份，显式分发：无计划任务维持 legacy，version=1 维持概述树，version=2 运行直接提取。未知版本明确拒绝，不按“非空 plan”猜测。分组计划已有自己的 version=2，与清单计划是不同契约。

保留 OutlineStore 的作业锁、request_id、attempt、来源快照、暂停/继续、原子候选发布。计划及窗口身份包含算法/提示/Schema 版本、来源与范围、影响窗口的预算配置；恢复不重新覆盖已完成结果。服务/预算改变时对剩余窗口重新检查，不能让已完成和新生成的语义身份混淆。

推荐最小增量存储：在 outline_batches 增加可空 `window_json`（主/辅范围、结构身份、风险等）及拆分父批关联；旧行继续按原 line_start/line_end 解读。V2 的 JSON 范围是权威，兼容行包络只用于定位，不能作为授权范围。父批 superseded 后由有效子批决定覆盖与完成；settle/resume/public_outline 必须识别该状态。

当前 `split_batch` 仅能切连续整行头尾，不能未经修改就处理多范围窗口或句段。V2 拆分操作应在同一短事务校验 job 状态和 attempt，保存完整子范围、废止父发布资格；模型调用仍在事务外。保留完成前来源版本检查与取消语义。

覆盖统计改为有效叶批主范围的集合并集，辅助范围不计入，父子不重复计入，未解析内容单列。分别展示处理覆盖、输出覆盖风险和语义质量未知；“请求成功/处理完成”不能显示成“全部知识已提取”。

## 7. 代码改动范围建议

| 模块 | 建议 | 原因 |
| --- | --- | --- |
| document_model / sources | 复用 | 解析和来源快照身份已存在，无需重写 |
| chunking / table_reading | 复用原文定位、表格依赖及可验证行结构 | 不改变检索 chunk 算法和向量缓存身份 |
| 新提取窗口模块，如 outline_windows.py | 结构拆分、主辅范围、预算打包 | 把确定性规划与模型执行分开测试 |
| plan_outline | 保留 V1 实现，增加版本明确的 V2 规划入口 | 旧任务可继续，新任务策略明确 |
| run_outline / run_adaptive | 版本分发，新增 run_direct_extraction | 不继续在摘要循环里叠加分支；V1 reduce_steps 保留 |
| validate_learning | 沿用文本与引用校验，V2 增加主范围锚点 | 格式正确、看过证据与属于本批是三个不同约束 |
| OutlineStore / public_outline | 增量窗口元数据、原子拆批、叶批覆盖 | 主辅范围不能直接塞进现有行数求和 |
| structured_output / 评测调用适配 | 可选记录真实 usage、耗时、协议回退与失败次数 | 当前请求函数主要返回解析对象，不能凭预算估算构造实际消耗 |
| Web / 前端 | 新清单选择 V2、显示风险和处理范围；总结入口另批交付 | 算法更新与产品可达性必须分别验收 |

## 8. 替代方案与判断依据

| 方案 | 优点 | 代价/限制 | 判断 |
| --- | --- | --- | --- |
| 全文一次请求 | 调用少，跨章节上下文直接可见 | 输入及输出有界，密集资料可能漏目标 | 小资料及输出需求有限时采用 |
| 固定行数/字符数分块 | 实现简单 | 格式敏感、可能切坏语义，也不能准确表示请求容量 | 不作为主策略 |
| 结构块 + 完整预算 + 直接提取 | 原文可追溯、确定性规划、没有必经摘要树 | 局部上下文有限，仍需输出压力与恢复设计 | 推荐清单 V2 默认 |
| 所有资料先多层摘要再提取 | 给每个局部窗口共享全局背景 | 前置串行依赖、额外调用、背景本身可能丢细节 | 保留 V1 对照和旧任务，不做 V2 默认 |
| 只取 RAG Top-K | 对局部问题便宜、相关性强 | 未检索到的章节无法保证覆盖 | 局部问答采用，不能独立承担完整清单 |
| Refine：带着上一版总结逐块改写 | 调用顺序简单 | 累积文本反复发送、顺序偏差、恢复及证据血缘更复杂 | 不作为默认完整提取流程 |

以上是工程取舍，不是已测性能排名。分块内容量、语义提取质量和跨章节效果需要项目资料验证。

## 9. 需要哪些验证

### 9.1 不消耗云端额度的正确性检查

可基于 `test_outlines.py`、`test_outline_context.py`、`test_table_reading.py` 增补：

- 每个可处理主范围恰好属于一个有效叶批；父批替代、恢复后无尾部丢失或重复候选。
- 标题/代码/列表/表格结构保护，表头及脚注实际交付，跨空隙引用拒绝。
- 辅助材料不能独自生成主目标；范围合法性不伪装语义充分性。
- 中英文长段落、单行超限、单行超宽表格、图片占位及 partial PDF 均有明确结果。
- 两种结构化协议都检查完整预算；Schema/支持文本增加后仍能安全缩批。
- 截断/上限命中不当成完整结果；有限拆分终止；模型返回空目标不被程序宣布为语义无遗漏。
- 暂停、来源替换、旧 attempt 晚到、崩溃恢复及旧 V1/legacy 任务继续有效。

这些测试证明代码契约，不证明真实目标召回。

### 9.2 小型真实 V1/V2 对照实验（尚未执行）

建议先选约 8–12 份可公开或用户授权资料作为诊断集：短笔记、长而稀疏资料、短而密集规范、跨章节定义/应用、表格/代码资料、结构不完整 PDF。数据量为实施建议，不是统计充分性承诺。

先固定提取粒度与目标清单参考，按文档或主题拆分调参集和保留测试集，不按同一本书的窗口随机拆分。语义参考应人工确认或明确标注 Agent 初标，并保存争议；不能用被测输出反向改标签。重复目标要区分同一概念的不同考察维度。

V1/V2 使用同一来源快照、任务指令、服务模型版本、输出需求和计数方法；记录协议、重试和缓存命中。先比较默认配置，再小范围测试窗口大小与辅助上下文；计数器升级另作一组。代表性样例可重复 2–3 次观察波动，小样本不宣称稳定 P95 或显著性。

| 指标 | 定义与证据 |
| --- | --- |
| 目标召回 | 参考目标中被正确覆盖的比例，单列关键目标与跨章节目标；未定义参考时不报这个百分比 |
| 目标有效性 | 生成目标是否受资料支持、范围是否合适、能否考察；防止堆目标刷召回 |
| 重复率 | 经统一规则判定的冗余目标占比，不把不同能力维度直接算重复 |
| 引用有效性 | 分开报告程序范围校验与人工语义支撑判断 |
| 处理覆盖 | 已处理主范围、未解析范围、未解决依赖、饱和窗口比例；不等同语义召回 |
| 模型消耗 | 供应商真实输入/输出 usage，若含缓存/推理字段分别保留；无 usage 标为未知，估计值单列 |
| 执行时间 | 首批有效候选、全部提取完成、可选归组完成的墙钟时间，失败/重试单列 |
| 恢复成本 | 中断后实际重跑窗口、重复消耗、已完成候选是否稳定 |

替换条件：关键目标/证据质量在预先约定的容忍范围内，成本或等待时间有实际改善，且无预算、越权引用或恢复回归。语义召回容忍范围需按使用目标确定，不能事后挑指标解释胜出。

### 9.3 能直接推导与必须实测的收益

V1 对分层文档的逻辑调用约为：N 次窗口概述 + R 次归并 + E 次提取；V2 约为 E' 次提取 + S 次拆分重做 + D 次可选依赖补读。协议回退和网络重试还会增加实际 HTTP 请求。

可直接确认的变化：V2 删除了必经的 N+R 类前置模型工作，能够更早开始产生候选。

不能直接确认：总 token、总费用、端到端时间一定下降，或召回一定提高。E'、S、D 和归组成本都可能增加；实际输出长度、缓存、服务波动也会影响结果。V2 减少了摘要作为前置背景传播错误的机会，但不消除直接提取本身的遗漏和错误。

## 10. 推荐实施顺序

1. **清单 V2-A：** 新版本计划、结构及预算打包、原文直接提取、主辅范围、输出风险/有限拆批、旧任务恢复兼容；维持当前行级引用边界。同步必要诊断。
2. **受控验证与小型对照：** 先通过离线契约检查，再以固定资料比较 V1/V2；确定窗口和补上下文的实际取舍。
3. **整理资料入口：** 复用已验证窗口机制，增加报告结果、章节展示与可选综合，并打通显式产品入口。
4. **按真实失败再扩展：** 超长单行精确片段、自动跨章节补读、聊天任务路由；每项有独立验收，不把它们都塞进首轮重构。

本次完成源码评审和设计文档，没有改动提取算法、数据库或运行服务，也没有执行真实模型对照实验。

## 11. 长上下文模型核验后的补充评审（2026-10-26）

### 11.1 模型容量与应用默认值不同

当日核对的 [DeepSeek 官方模型页](https://api-docs.deepseek.com/quick_start/pricing/) 标注 deepseek-flash 对应 DeepSeek-V4.1-Flash-1017，具有 1M 上下文和最高 384K 输出。[官方模型元数据接口文档](https://api-docs.deepseek.com/api/list-models/) 的例子给出 context_window=1048576、max_output_tokens=393216，并明确上下文容量计入输入和输出。

这些是官方服务能力，不证明任意同名中转/自部署端点也提供相同容量。本轮未读取私有 .env，未请求带密钥的模型接口，未核验运行服务实际生效的模型/预算配置。

`GenerationBudget.from_env` 未配置时回退到 32768/4096/2048，得到输入额度 26624；计数依据仍是完整请求 UTF-8 字节及协议余量。这不是实际模型的 token 容量识别。若运行服务沿用默认值，会同时受到偏小的容量及保守估算限制。

### 11.2 改成 1M 配置不足以改变当前算法

`plan_outline` 还要求 expected<=6、expected*950<=output_tokens；默认输出 4096 时，expected=5 就不能走全文路径。分层初始窗口仍受 80 行限制，概述最多 6 点，提取最多 4/6 个目标。这些限制独立于模型上下文容量。

因此，不能用当前 32k 配置下“被迫分层”的运行结果证明多层概述算法对 1M 模型必要；应先建立容量与输出契约合理的基线，再判断算法收益。此前任何默认采用较小窗口的建议都是待验证的执行策略，不是已证明的最优值。

### 11.3 推荐将三个预算概念分开

- 模型硬限制：按实际端点/模型的可靠元数据或显式配置获取 context_window、最大输出及计数身份。官方接口支持元数据发现不意味着所有兼容服务都有此能力；未知服务保留有标签的回退。
- 产品执行软限制：交互问答与后台资料处理可有不同的成本、等待时间和单次输入政策；若人为限制为 32k/其他值，应显示为应用策略，不能称模型不支持。
- 任务输出需求：总结的详细程度、清单提取粒度和最大目标数分别决定输出预留与拆分。支持 384K 输出不意味着每次都预留 384K；只扩输入、不调整 4/6 个目标契约也不能保证覆盖。

V2 优先以原文直接请求建立基线：完整任务符合实际预算且输出需求适合时采用一次请求；因输出密度、成本/等待政策或超过容量而需要拆分时采用结构化窗口直接提取；最后的全局综合仅由总结任务需要触发。该规则允许较大原文窗口，不预先假定大资料都应先摘要树或都应拆成小块。

### 11.4 对照实验必须分离容量收益和算法收益

至少保留三组：A 为原配置/原算法诊断；B 为核实服务容量、合理输出设置后仍使用 V1，观察哪些固定阈值继续触发分层；C 为同一模型容量、计数方式和输出要求下的 V2 直接提取。另可在适合的资料上加入单次原文直接处理基线。

B 与 C 用于判断概述树是否有价值；A 与其他组的差距不能全部归因于 V2。质量参考、实际 token、费用、首批/完成时间及恢复成本仍按第 9 节记录。允许长上下文不等于保证完整提取，当前没有项目实测支持最佳窗口大小或任一算法必然胜出。
