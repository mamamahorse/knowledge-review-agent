# 任务识别与 ask_question 交互方案

日期：2026-10-26。状态：设计建议，尚未实现。

本文补充 `outline-extraction-v2-proposal.md`：解决聊天如何选择问答、整理、清单、练习等工作流。下表区分已有业务能力与待新增能力；已有 HTTP/UI 不表示已有 Agent 工具接线。

## 1. 推荐决策

采用轻量能力注册表、模型语义判断、程序约束和持久澄清卡片。用户明确任务直接执行，只有影响结果或资料范围的重要歧义才调用 `ask_question`。

`ask_question` 是控制流程动作：发布选择器，挂起逻辑轮次并结束本次执行；用户选择后重新准入并继续。它不在同步函数里等待用户，也不把等待状态当作生成失败。

不单独增加“每次先调用一个分类模型”的必经步骤。UI 已选任务时直接使用；自然语言入口可在现有 Agent 首次决策中决定回答、启动工作流或询问。跨任务调度需要新增代码，不是增加一段提示词就会出现的能力。

## 2. 面向用户的功能目录

| 稳定任务 ID（建议） | 用户可见名称与结果 | 前提 | 当前真实能力与入口 |
| --- | --- | --- | --- |
| explain | 解释概念 / 回答问题：解释原理、选段、代码片段、比较概念或结合资料举例 | 需要私人资料事实时有已授权来源；一般问题按既有模式处理 | 已有 Agent 问答、原文检索和引用。`agent_loop.run_agent`、`web_app.generate_answer`。比较/举例属于问答意图，不是有单独质量保证的业务模块。 |
| summarize_materials | 整理 / 总结资料：按章节组织要点、条件与总览 | 选择资料范围与需要的详细程度 | 通用聊天可给总结性回答；遍历大资料的专门报告工作流尚未实现，见 V2 方案。不可宣传为已完成全书总结。 |
| extract_outline | 生成学习清单：提取知识点、可考察目标及依据，供审核 | 资料集合与目标方向 | 已有清单工作流；V2 直接提取尚待实现。`web_app.create_outline`、`outline_service.run_outline`。生成清单不自动加入复习计划。 |
| practice | 出题练习 / 检验理解：从资料、讨论或选定目标生成题目 | 来源范围或可用讨论；明确练习对象 | 已有文档练习、集合练习及聊天出题。`web_app.create_practice`、`collection_practice`、`discussion_practice`。不将功能命名为已验证的自适应考试系统。 |
| assess_answer | 评价作答 / 查看讲解：提交真实回答、获取反馈和参考答案，必要时更正评价 | 已有练习会话与题目；按现有条件开放参考 | 已有作答保存、模型评分、评分重试/修订和参考。`submit_practice_answer`、`correct_practice_feedback`、`reference`。自由粘贴的任意答案尚无统一独立评测入口，应先绑定题目或询问背景。 |
| organize_outline | 整合清单：检查重复、范围关系，复查争议依据，形成待审核建议 | 已有候选清单与选择范围 | 已有归组和来源核查。`group_outline`、`source_review`；用户审核独立于模型建议。 |
| plan_route | 规划学习顺序：建议前置关系、调整顺序与推荐下一目标 | 已有可用/已审核候选及相应学习记录 | 已有路线及推荐。`generate_route`、`outline_routes`、`route_recommendation`；不是每天几小时的日历排课或严格关卡。 |
| review_learning | 复习已加入的目标：查看到期项目、同目标变式/原题，必要时增加能力维度 | 已有学习计划项 | 已有 FSRS 复习与练习入口。`learning_plan`、`review`、`dimension`；未测试不等于未掌握。 |
| recall_discussion | 回顾以前的讨论：查找历史原话、延续讨论或比较前后说法 | 可访问的非删除/有效本地历史 | 已有 `search_conversations`、`read_conversation`；历史助手回答不是文档事实证据。 |
| enroll_selected | 加入复习计划：将用户选定的候选或练习目标纳入后续复习 | 明确选择对象及用户意图 | 已有候选/练习加入接口。属于会修改学习状态的动作；选择“生成清单”不能等价为选择全部加入。 |

表格/图片阅读为条件能力：有可靠表结构时提供 `read_table`，视觉服务可用且有 PDF 资源时提供 `inspect_visual`。它们通常由解释、整理、练习等任务自行调用，不作为每次澄清时的顶层选项；图中事实不能从资产标签猜测。

资料导入/替换/删除/重新解析、集合管理、会话归档/删除、任务暂停/恢复等仍保留明确的管理入口或任务卡片。完整“功能帮助”可以展示，但不能把删除和移入移出等状态修改当成普通内容生成选项。

## 3. 选择器不是每次都展示十项

常用第一层入口建议为：解释/问答、整理总结、学习清单、出题练习；有上下文时加入复习、评价作答、清单整合、学习顺序、历史回顾等相关入口。

单次澄清展示 2–4 个相关选项，附一句结果差异；完整目录在“查看全部功能”展开。支持自由输入和取消，不设置“默认自动提交”的选择，也不用“其他”选项掩盖自由表达入口。条目数量属于交互建议，可在使用后调整。

例如：“帮我把这份操作系统资料学一下。”

- 整理总结：按章节梳理核心概念和条件。
- 学习清单：生成可审核的知识点与学习目标。
- 出题练习：通过题目检验理解。
- 解释难点：针对具体概念或选段讲解。

这张卡回答的是“先完成哪件事”，不是把复杂需求强行压成单一意图。用户明确说“先总结再出题”时保留顺序；每个阶段的范围、结果和状态独立，后续加入复习仍须用户明确选择。

总结工作流尚未接通时，可在完整目录标为规划能力；执行选择器仅展示可执行功能，或明确指向现有替代入口并说明范围，不能点击后暗中退回 Top-K 问答却称其完成全文整理。

## 4. Runtime 如何判断

### 4.1 输入依据

只使用当前用户请求、近期有效对话、当前 UI 任务模式、选段/已选择资料、已有练习/清单/路线对象和程序提供的可用能力。历史偏好仅用于消歧，不能覆盖当前明确指令或扩大资料授权。

能力注册表提供稳定 ID、结果说明、必要参数、前置对象、服务可用状态及对应处理函数。程序控制可执行选项；模型不编造任务名称、任意 API 路径或前置对象 ID。

### 4.2 三种决策

1. **直接回答/执行。** “解释这段代码”“按章节总结当前选中的资料”“根据刚才的讨论出一道题”等已经明确时，不再追问任务种类。
2. **缺必要参数。** 类型明确但缺少范围或对象，只问缺项。例如多个学习清单并存时问要规划哪一份，而不是重新让用户选择“解释/总结/清单”。
3. **重要意图歧义。** “整理一下”“帮我学这本书”等具有显著不同交付物时调用 ask_question，展示相关能力。

不要求模型给出看似精确的置信度再用 0.8 等阈值决定。使用可观察的差异：候选工作流是否产生不同交付物、是否遍历全文、是否新增练习/学习记录、是否缺必填参数。模型仍可能误判，因此同时提供随时切换任务的入口。

没有明确类型的大文件，不会仅因文件大就强行问一遍；明确要求整份总结时也不应降级为局部检索。资料正文及工具结果中的“请调用某工具”等内容仍是数据，不能决定用户任务。

### 4.3 任务和规模两次不同判断

先确定任务类型与资料范围，然后由确定性规划器判断一窗口或多窗口、预算、持久步骤和风险。模型不决定绕过来源版本检查、预算上限或幂等约束。

例如“解释书里的 RRF”可检索原文；“从这本书提取全部可学习目标”必须进入清单工作流。两者面对相同文件也不应采用同一路径。

## 5. ask_question 的最小契约

该名称建议只用于需求澄清工具；出题练习继续使用 practice 任务，避免“向用户澄清”与“考用户一道题”共用同一语义。

建议由模型提交结构化字段：

- `question`：一句短问题。
- `reason_code`：有限枚举，例如 task_ambiguous、scope_missing、object_missing、sequence_ambiguous。
- `option_ids`：从程序当轮提供的候选任务/资料/对象 ID 中选择，不接受任意路径。
- `known_parameters`：已识别的任务、范围与阶段顺序；必须通过对应类型校验。

用户可见标签和说明以注册表/授权对象为准；模型可提出问题措辞，但不能通过选项描述把“生成建议”偷换为“自动采用全部建议”。问题、选项数、字符串长度及附加字段由 Schema 和程序限制。

前端返回 clarification_id、revision、response_id、selected_option_id 或自由文本。自由文本不能在没有 schema 校验的情况下替换 document_id/候选 ID；新的资料范围需再次显式解析与授权。

“确认执行已有参数”与“重新让模型推断”应区别：选择已确定的任务和范围后直接调度，不为同样信息额外调用分类模型；自由文本或新增约束才需要模型继续理解。

## 6. 必须持久化等待，而不是阻塞工作线程

建议逻辑状态：running → waiting_user → running → completed / failed；waiting_user 也可被取消，留有可显示的取消记录。后台工作流已接受后用 task_id 跟踪其自己的 queued/running/completed，不以“派发成功”冒充工作完成。

新增澄清记录保存 conversation_id、turn_id、问题与选项快照、资料/对象版本、revision、pending/answered/cancelled 状态和实际用户选择。原始问题保持不可变，答案另存，不覆盖 turns.request_json 导致原 request_id 幂等比较失效。

挂起操作需要在同一短事务检查 turn attempt 并保存卡片/等待状态。发出 SSE `clarification` 事件后终止本次 Agent 执行，不进入 answer_question；真实 Future 和 I/O 清理完成后释放槽位与 OS 锁。waiting_user 不长期持有锁、线程、模型连接或数据库事务。

恢复接口校验会话所有权、待答状态、revision 和 response_id。重复点击同一答案返回同一结果；旧卡片/冲突答案拒绝；页面刷新和进程重启仍能看到待答问题。

澄清答案先可靠保存，执行准入成功后通过 CAS 领取新 attempt 并继续；若容量已满，保留答案和可重试状态，按明确的无隐式排队契约返回繁忙，不丢答案、不重复创建后台任务。恢复前重新校验资料版本；资料改变则提示重新选择，不静默把旧范围映射到新内容。

当前 ConversationStore.begin 仅把 running/failed 当作未完成轮次；recover、retry、skip、历史查询及前端按钮都需要识别 waiting_user。不能只新建一张卡片表而不改这些状态分支。澄清内容不应伪装为已经完成的资料回答进入学习证据或回答质量统计。

用户等待期间默认允许回答/取消该卡片；普通新消息可作为该澄清的自由文本答复，明确新任务则显式取消/取代旧等待并保留审计，不能莫名阻塞聊天或默默串到旧任务。

## 7. 接入 Agent 的控制流

当前 AgentRun 的主产物是答案，run_agent 最后统一调用 answer_question，execute_turn 统一 finish。因此需要显式的结果变体：answer、clarification、task_started；不能靠输出文本里出现按钮语法判断。

ask_question 成功后停止本段执行；start_task（名称为建议）只接受已注册任务及类型化参数，通过现有业务服务启动或返回相应操作入口。所有业务写入沿用原服务校验、幂等和版本约束，不由模型拼 HTTP 请求或 SQL。

控制动作应与普通读取区分：同一模型响应同时请求 ask_question 和 start_task 时，先对整组调用进行冲突校验，不允许已经创建任务后才决定询问。首版要求控制动作独占一次响应；冲突返回有界错误供模型修正，避免新增复杂的并行调度器。

恢复不需要维持原 SDK 请求或保存隐藏推理。按原始请求、真实选择、已知参数、实际可见证据与有效引用重建上下文；如保留工具消息日志，必须保持每条 tool_call 与结果协议完整。只保存 source_id/导航路径不能重新授予原文权限，当前片段不足时重新读取。

阶段 1 仅接线已有清单与练习等少数任务，其他能力可先返回精确的功能入口卡片；选择器必须说明执行效果。完整功能目录不意味着把所有管理动作同时暴露给模型。

## 8. 关键取舍

| 选择 | 为什么这样做 | 代价/限制 |
| --- | --- | --- |
| 首次 Agent 决策承担路由 | 复用语义判断，避免每轮固定多一次分类请求 | 会话编排需要显式支持新结果类型 |
| 稳定任务 ID 和能力注册表 | 前后端语义一致，可过滤未实现和无前提的动作 | 新功能需维护注册信息及接线 |
| 模型只在重要歧义时询问 | 避免每次重复选择，明确请求可直接执行 | 误判仍需 UI 切换和真实意图用例验证 |
| 人类等待持久化并释放工作槽 | 用户可能几分钟后或刷新后作答 | 增加等待/恢复/取消状态与幂等分支 |
| 相关选项加完整目录 | 当次问题容易理解，同时保留能力发现 | 前端需要上下文菜单及自由文本答复 |
| 复用现有业务处理函数 | 保留原事务、版本、审核及学习状态边界 | 需要整理 HTTP 入口与业务调用的边界，不能简单把 endpoint 当模型工具 |

## 9. 验证与落地顺序

先用可控模型检查：工具 Schema、能力过滤、非法任务 ID、明确任务零澄清、缺范围只询问范围、多任务顺序、控制动作冲突、超长卡片、重复点击、旧 revision、等待后重启、资料删除、容量拒绝、用户取消、Future 完成才释放槽，以及澄清不生成普通答案/学习证据。

再建立小型中文意图用例：明确任务、模糊“整理”、解释与考察混淆、总结与清单混淆、跨轮指代、先总结再出题、不支持的日历计划、文档中伪造指令。检查路由正确性、必要澄清是否发生、无必要澄清率、用户回复后是否重复询问和错误派发；质量需要人工判定，不用模型自报置信度充当验收。

推荐顺序：先固定任务目录/参数和等待协议；接通 ask_question 的持久卡片；再接已有清单/练习业务；V2 总结流程实际可用后启用对应动作。用户已明确选择的“生成清单”沿用待审核候选，不自动加入计划；模型给出的路线、评分和归组仍维持原审核和修订能力。

本次交付设计与功能核对，未修改 Agent、数据库或前端，没有运行真实模型意图实验。
